# Crosser puzzle guide

How puzzles are made, validated, rated, and how future generation should learn from ratings.

## Files
- `tools/puzzles_src.json` – source of truth. Each puzzle: `id, title, author, date, grid` (rows, `#` = block),
  `clues` keyed by ANSWER (or `ANSWER/a`, `ANSWER/d` if an answer is clued differently by direction),
  `phrases` (multi-word entries not in the word list), and `meta`:
  `difficulty` (easy/medium/hard), `themeType` (themeless, added-word, starts-with, hidden-word, …),
  `clueStyle` (straight, wordplay-heavy, mixed), `notes`.
  Cross-references are written `{A:ANSWER}` / `{D:ANSWER}` and resolved to numbers at build.
- `tools/build.py` – validates and writes `puzzles.js`. Run `python3 tools/build.py`; it must print `ok` for every puzzle.
- `tools/enable1.txt` – public-domain ENABLE word list used to verify every non-theme entry is a real word.
- `tools/quality.py` – fill-quality and reuse checks (below), used by `build.py` and `ingest.py`.
- `tools/stoplist.txt` – **contains answers (spoilers)**. Overused answers to avoid; regenerated by
  `tools/make_stoplist.py` after every ingest. Constructors must read it; never show it to solvers.
- `tools/ingest.py` – the only way new puzzles go live. Append-only; rejects anything that fails a hard rule.

## Quality bar (published-crossword standards)
- 180° rotational symmetry, all cells checked, no 2-letter entries, connected grid.
- 15x15 themed: ≤78 words, ~36–42 blocks; 11x11: ≤44 words; minis: 5x5, 10 entries.
- Coherent theme with a revealer or a title that unlocks it.
- Fill: common, lively words; avoid crosswordese (ESNE, ALEE…), obscure abbreviations, partials, roll-your-owns, and offensive words (see `bad.txt` in the generator).
- Clues: all original; vary types (definition, fill-in-the-blank, wordplay with `?`, misdirection); never reuse a clue verbatim across puzzles.

## No-repeat rules (enforced by `tools/quality.py`; hard failures at ingest)
Within one puzzle:
- (a) **No duplicate answers.** The same answer may not appear twice.
- (b) **No shared roots.** No answer may contain another answer of 4+ letters (including inside a long phrase,
  e.g. a short answer that is also a word inside a theme entry), and no two answers may be forms of the same word
  (plural/tense/-er/-ing variants, or prefix variants like UN-/RE-/A- + the same base). The only exception is an
  intentional theme device shared by the theme entries; say so in `meta.notes`. The validator also prints
  "share a chunk — check by hand" warnings for long common substrings; resolve them before submitting.
- (c) **No echoing clues.** A clue may not contain its own answer (or a form of it), and may not contain the answer
  of any entry that crosses it. Avoid using any other answer in the grid in a clue (warning).

Across puzzles (checked against the entire live backlog in `tools/puzzles_src.json`):
- (d1) **Never reuse an answer + clue pair.** If an answer has been used before, it needs a brand-new clue.
- (d2) **Reuse caps** (answers already used in ANY live puzzle):

  | Size | Repeated answers of this length or more | Max | Max repeats of any length (3+) |
  |---|---|---|---|
  | Mini (5x5–7x7) | 4+ letters | 1 | 2 |
  | Midi (11x11–12x12) | 5+ letters | 2 | 6 |
  | Full (13x13–15x15) | 5+ letters | 3 | 10 |

  Limits were tuned on the Oct 25 2026 backlog (16 live puzzles): most live puzzles already met them, so they are
  achievable, while the worst offenders would have been stopped.
- (d3) **Stoplist.** Do not use any answer in `tools/stoplist.txt` (answers of 4+ letters already in 2+ live puzzles,
  or any answer in 3+). Stoplist hits are reported as warnings and almost always also count against the caps.
- Prefer fresh fill: before finalizing, run `python3 tools/ingest.py --dir <tmpdir> --dry-run` and rework any slot it lists.

Live puzzles are never edited (append-only), so `build.py` lists their rule violations as "grandfathered" notes
instead of failing; `python3 tools/build.py --strict` turns them into failures.

## Ratings (in-app)
After solving (in the congrats modal) or from the archive (“Rate” link on each card) a solver gives 1–5 stars,
optional tags (`fun, great theme, clever clues, smooth fill, too easy, too hard, obscure fill, boring clues, weak theme`) and a note.
Ratings are stored in `localStorage` key `xw:ratings`. The archive's **Export ratings.json** button downloads:

```json
{ "schema": "crosser-ratings/1", "exportedAt": "...",
  "ratings": [ { "puzzleId": "...", "deviceId": "d-…", "stars": 4, "tags": ["clever clues"], "note": "...",
                 "ratedAt": "...", "solved": true, "solveTimeSec": 312, "usedReveal": false,
                 "meta": { "title": "...", "size": "15x15", "difficulty": "medium",
                           "themeType": "starts-with", "clueStyle": "mixed", "wordCount": 76, "source": "original" } } ],
  "puzzles": [ { "id": "...", "title": "...", "size": "...", "difficulty": "...", "themeType": "...", "clueStyle": "...", "wordCount": 76 } ] }
```
Every save (end-screen **Submit & Home** or the archive **Rate** popup) also syncs automatically: the app POSTs a
full snapshot of all ratings (same schema, `kind: "snapshot"`, split into <3.5 KB parts) to the private ntfy topic in
`SYNC_URL` in `app.js`. It is fire-and-forget (fetch `keepalive`), never blocks navigation, and fails silently. On
app load it re-sends if ratings changed since the last successful sync, or if the last sync is over 6 h old (ntfy
only caches about 12 h). The Export button still works as a manual backup.

**Devices.** Each browser/device generates a persistent random id on first use (`localStorage` key `xw:deviceId`,
`d-` + 24 hex chars). It is stamped on every rating and on every snapshot (`"deviceId"` at the top level of the
message), so ratings from a phone, a laptop and a tablet are all counted. Snapshots or `ratings.json` entries from
older app versions with no id are treated as one legacy device (`"legacy"`).

## Ratings pipeline (box side)
```
python3 tools/pull_ratings.py      # ntfy -> /workspace/crossword/ratings.json (gitignored, local only)
python3 tools/ratings_brief.py     # ratings.json + puzzle meta -> /workspace/crossword/ratings_brief.md (gitignored)
```
`pull_ratings.py` is idempotent and keys ratings by **(deviceId, puzzleId)**. Within one device the newest `ratedAt`
wins (re-rating a puzzle edits that device's rating). Across devices **every rating is kept**; two devices rating the
same puzzle are two ratings. Old `ratings.json` files (keyed by puzzle only) are migrated in place with their entries
assigned to the legacy device, and ratings are never dropped. The only fold is a legacy copy whose puzzleId and
millisecond `ratedAt` exactly match a device-stamped rating: that is the same rating re-sent by an updated app.
Run it every few hours so nothing ages out of ntfy's cache. Constructors read `ratings_brief.md` before every build.

## How future generation should use ratings
Asymmetric: **steer away from what made bad puzzles bad more than you try to replicate good ones.**
Negative signals (1-2★, negative tags) weigh about **2x** positive ones (3★ counts 0.5x; the last 14 days count x1.5).
Every device's rating counts as its own rating in all weighting and aggregation (tag weights, category means,
per-puzzle averages and `n`). When avoidance and replication conflict, avoidance wins. **Diversity is preserved**: feedback removes flaws, not variety.

1. **AVOID targets specific flaws and execution problems, never whole categories.** Examples: obscure fill and
   crosswordese, flat or boring clues, a weak or loose theme (themers that don't follow the rule exactly, an
   unclear payoff), difficulty that misses its label, unfair crossings (Reveal used), and glue-heavy grids.
   Tag fixes: `too easy` → more misdirection and `?` clues, fewer fill-in-blanks; `too hard` → fair crossings for
   rare words and names; `obscure fill` → higher frequency cutoff, rework corners, add flagged words to the stoplist;
   `boring clues` → livelier angles, 25-40% wordplay; `weak theme` → tighten execution and consider a revealer.
2. **A single low-rated puzzle never bans its theme type, size, difficulty or style.** Fix the flaw it showed.
   A category is disfavored only if it is **consistently low across 3+ ratings** (mean ≤2.5★, ≥2/3 of them low),
   and even then it is only **down-weighted** (used about half as often). It is never excluded.
3. **Lean toward** the *qualities* behind 4-5★ ratings (tight themes, clever but fair clues, smooth fill). This is a
   smaller signal, and **positive ratings must not narrow the mix toward copies**: don't reuse a theme mechanism,
   clue gimmick or grid pattern just because it rated well.
4. **Diversity (required).** `ratings_brief.md` lists the mix of the last ~10 puzzles (theme mechanisms, difficulty,
   clue styles, sizes, grid shapes and word/block counts). Vary it: don't repeat the same theme mechanism, clue style or grid
   shape back-to-back; a full-size theme mechanism should differ from the previous two; if ≥70% of recent puzzles
   share a difficulty or clue style, change it soon. About 1 puzzle in 5 may be **exploratory**, using an untried
   mechanism, style or shape, held to the same quality bar.
5. Read free-text notes for specific complaints (a named word or clue) and add them to the stoplist or clue notes.
6. Record in the new puzzle's `meta.notes` which brief items were addressed, so the effect shows in later ratings.

## Generator
The fill engine lives in `/workspace/gen` (box scratch): `fill3.py` (arc-consistent backtracking filler over a
wordfreq∩ENABLE list ranked by frequency) and `hunt.py` (searches symmetric block patterns around fixed theme entries).
Words from minis/themed grids are then hand-reviewed and every clue is written by hand.
